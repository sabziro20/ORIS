# Многопоточный сервер задач

Клиент-серверное приложение на Python для управления общим списком задач. Сервер одновременно обслуживает несколько клиентов, все клиенты работают с одним и тем же списком, который хранится на сервере.

Используются: TCP-сокеты, `threading`, общий изменяемый словарь задач и блокировки (`threading.Lock`).

## Структура проекта

| Файл | Назначение |
|------|------------|
| `server.py` | Сервер: принимает подключения, хранит общий список задач, обрабатывает команды |
| `client.py` | Клиент: консольный интерфейс, отправляет команды и выводит ответы сервера |
| `protocol.py` | Общий протокол обмена сообщениями (формат пакета, отправка и приём) |

## Как запустить

Требуется Python 3.8+, сторонние библиотеки не нужны.

1. Запустить сервер (по умолчанию слушает порт `5555`):

   ```bash
   python server.py
   ```

2. В отдельном терминале запустить клиент (можно открыть несколько клиентов в разных терминалах):

   ```bash
   python client.py
   ```

3. Ввести имя пользователя (оно должно быть уникальным среди подключённых клиентов) и работать с командами.

По умолчанию клиент подключается к `127.0.0.1:5555`. Если сервер запущен на другой машине, нужно изменить `HOST` в `client.py`.

## Поддерживаемые команды

| Команда | Действие |
|---------|----------|
| `/add <текст>` | Добавить новую задачу |
| `/list` | Показать все задачи |
| `/done <номер>` | Отметить задачу с указанным номером как выполненную |
| `/quit` | Завершить работу клиента |

Пример вывода `/list`:

```
1. [ ] Купить кофе
2. [x] Подготовить домашку
3. [ ] Посмотреть лекцию
```

### Обработка ошибок

Сервер возвращает клиенту сообщение об ошибке (клиент выводит его как `[ошибка] ...`), а не завершается с исключением, в следующих случаях:

- `/add` без текста задачи;
- `/done` с некорректным аргументом (не число, пустой аргумент);
- `/done` с номером несуществующей задачи;
- неизвестная команда;
- повторное или пустое имя пользователя при подключении;
- обрыв соединения клиентом (сервер корректно убирает клиента из списка).

## Протокол обмена

TCP — потоковый протокол, поэтому границы сообщений нужно задавать самим. Каждое сообщение состоит из:

- заголовка 8 байт (`!4sI`): 4 байта — имя команды (`JOIN`, `ADD`, `DONE`, `LIST`, `QUIT`, `TEXT`, `ERRO`), 4 байта — длина данных (big-endian);
- данных (payload) указанной длины в UTF-8.

Функция `recv_exact` в `protocol.py` читает ровно столько байт, сколько нужно, в цикле, так как один вызов `recv` может вернуть меньше данных. Максимальный размер сообщения ограничен 10 МБ.

## Как реализована одновременная работа нескольких клиентов

Главный поток сервера в бесконечном цикле вызывает `server.accept()`. Для каждого нового подключения создаётся отдельный поток (`threading.Thread`) с функцией `handle_client`, которая в цикле читает команды именно этого клиента и отвечает ему. Благодаря этому медленный или «молчащий» клиент не блокирует остальных. Потоки помечены как `daemon=True`, поэтому при остановке сервера они завершаются вместе с ним.

На стороне клиента тоже два потока: основной читает ввод пользователя и отправляет команды, а фоновый поток `listen_loop` постоянно принимает сообщения от сервера и печатает их. Так клиент может получать уведомления (например, о том, что кто-то присоединился или вышел), не дожидаясь ввода.

## Где и зачем используется синхронизация

Все потоки-обработчики работают с общими данными, поэтому доступ к ним защищён блокировками `threading.Lock`:

- **`tasks_lock`** защищает общий словарь задач `tasks`. Блокировка берётся при добавлении задачи (`/add`), при изменении статуса (`/done`) и при чтении списка (`/list`). В `/done` получение списка ключей, проверка номера и изменение статуса выполняются внутри одного блока `with tasks_lock`, чтобы список не изменился другим потоком между проверкой и изменением (иначе возможна гонка данных).
- **`clients_lock`** защищает словарь подключённых клиентов `clients`. Он нужен при регистрации клиента (проверка уникальности имени и добавление выполняются атомарно), при удалении клиента после отключения и при рассылке сообщений. В `broadcast` список получателей копируется под блокировкой, а сама отправка выполняется уже вне блокировки, чтобы медленная сеть не удерживала lock и не тормозила другие потоки.

Без этих блокировок два клиента, одновременно добавляющие или отмечающие задачи, могли бы повредить общие данные или получить некорректный результат.
